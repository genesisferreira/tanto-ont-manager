# Contrato de autenticação — ZTE F6201B V9.3.10P8N1

Identificação: `0.1.3-lab — leitura autenticada completa`

Modelo: ZXHN F6201B  
Firmware esperado (quando disponível): Software `V9.3.10P8N1`  
Adaptador: `ZteF6201BV9310P8N1AuthenticationAdapter`  
ID: `zte-f6201b-v9.3.10p8n1-auth-v1`

Este documento descreve o contrato observado na página pública real e nos assets GET do mesmo IP. Não contém credencial, cookie, token reutilizável, challenge, serial completo nem MAC completo.

## Evidências de origem

- Pacote público: diagnóstico `20260814-114711_192-168-100-x_bfb664b9.zip`
- Página: HTTPS `192.168.100.1/` status 200, título `F6201B`, ~155.971 bytes
- Análise inicial: somente GET; nenhum POST de login durante o mapeamento
- Assets públicos referenciados pela página, mesmo IP:
  - `/jquery/jquery.min.js`
  - `/jquery/crypto-js.min.js`
  - `/jquery/jsencrypt.min.js`
  - `/jquery/common_lib.js`
  - `/?_type=loginData&_tag=login_entry` (JSON de bootstrap)
  - `/?_type=loginData&_tag=login_token` (XML de challenge; valor não registrado)

## Formulário visível (não é `<form action>`)

Não há elemento `<form>` com `action` estático. O login é AJAX disparado pelo botão `#LoginId`.

Campos observados:

| Papel na UI | `name` / `id` | Tipo | Enviado no POST? |
|---|---|---|---|
| Usuário | `Frm_Username` | text | Não com esse nome. O POST usa `Username` = valor do campo |
| Senha | `Frm_Password` | password | Não em claro. O POST usa `Password` = SHA-256(senha + challenge) |
| Token de sessão | `_sessionTOKEN` | hidden | Sim, campo `_sessionTOKEN` |
| Botão | `LoginId` | submit | Clique explícito |

## Sequência observada no JavaScript público

1. No `$(document).ready`, GET JSON `/?_type=loginData&_tag=login_entry`.
2. A resposta JSON preenche `#_sessionTOKEN` com a chave `sess_token` (valor não registrado).
3. Chaves JSON públicas observadas (sem valores): `sess_token`, `loginErrMsg`, `lockingTime`, `promptMsg`.
4. Clique em `#LoginId` (com throttle 300 ms) faz GET `/?_type=loginData&_tag=login_token`.
5. A resposta é `text/xml`. Elemento raiz: `ajax_response_xml_root`. O texto interno é o challenge.
6. Algoritmo client-side: `SHA256Password = sha256(Password + xmlObj)` (concatenação direta; SHA-256 padrão do `common_lib.js` / CryptoJS).
7. Único POST permitido: `/?_type=loginData&_tag=login_entry`, `application/x-www-form-urlencoded`, campos:
   - `action` = `login`
   - `Username` = usuário informado
   - `Password` = hash hex
   - `_sessionTOKEN` = token da etapa 2
8. Sucesso: JSON com `login_need_refresh` verdadeiro → o browser recarrega `/` no mesmo IP.
9. Falha: `DisplayLoginErrorTip` usa `loginErrMsg`, `promptMsg` e `lockingTime`. A interface da ONT não separa “usuário inexistente” de “senha incorreta”.
10. Cookie de sessão: GET de `login_entry` define um cookie HttpOnly/Secure em `Path=/`. Nome observado: `SID_HTTPS_`. Valor nunca registrado. Deve permanecer só em `CookieContainer` na memória.
11. Logout observado no JS: POST `/?_type=loginData&_tag=logout_entry` com `IF_LogOff=1` e `_sessionTOKEN`. Sucesso: JSON `need_refresh` ou corpo não-objeto com recarregamento. Usado somente no clique em `Encerrar sessão`.

## Redirect esperado

- Sucesso: recarregar a mesma origem (`top.location.href = top.location.href`), isto é, GET `/` no mesmo IP.
- Redirect para outro host é rejeitado.

## Marcadores de sessão autenticada

A página pública já contém `function LogOff` e o shell SPA. Por isso `LogOff` no HTML **não** prova login.

Evidências combinadas de sucesso:

1. HTTP 200 no POST de login;
2. `login_need_refresh` verdadeiro;
3. cookie de sessão presente em memória;
4. `loginErrMsg` / `promptMsg` vazios;
5. GET posterior no mesmo IP com o cookie, sem repetir o POST.

## Leitura autenticada (somente GET)

O JS da interface autenticada carrega cada tela em dois GETs observados:

```text
GET /?_type=menuView&_tag={template}&Menu3Location=0
GET /?_type=menuData&_tag={lua.lua}&_={cache}
```

O `menuData` lua sem o `menuView` correspondente devolve XML genérico de ACK (HTTP 200, sem ParaName). A leitura automática replica essa sequência. `$.get` do firmware envia `X-Requested-With: XMLHttpRequest`; o HttpClient da sessão adiciona só esse cabeçalho e `Referer` da origem vinculada. `_sessionTOKEN` não entra no GET.

Allowlist desta firmware:

- `GET /`
- `GET /?_type=loginData&_tag=login_entry` (bootstrap do token, sem senha)
- `GET /?_type=loginData&_tag=login_token` (challenge, só durante o clique de Login)
- `GET /?_type=menuView|menuData|hiddenData&_tag={tag}` somente se `{tag}` foi classificada `SafeRead` na UI autenticada

Bloqueio de tags/rotas associadas a: Apply, Save, Submit, Create, Delete, Remove, Reset, Reboot, Upgrade, Upload, Restore, Factory, Firmware, Password, Account, Write, Set, Modify.

## Logout oficial

- Endpoint: POST `/?_type=loginData&_tag=logout_entry`
- Campos: `IF_LogOff=1`, `_sessionTOKEN`
- No máximo um POST de logout por sessão, somente ação do operador
- Cookies são descartados mesmo se a invalidação remota não for confirmada

## TLS

Exceção self-signed somente para o IP selecionado. A sessão autenticada fica vinculada ao IP e à impressão SHA-256 do certificado observada na detecção. Se a impressão mudar, a sessão é encerrada.

## O que esta fase não faz

- POST de configuração, WAN, PPPoE, VLAN, TR-069, reset, reboot, firmware
- Telnet/SSH
- Credenciais padrão, brute force ou endpoints não observados
- Persistência de senha, cookie ou token
